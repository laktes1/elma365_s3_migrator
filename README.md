# elma365_s3_migrator

Миграция объектного хранилища ELMA365 с MinIO на новое S3 на физическом сервере. Текущая схема: шлюз `s3gw` записывает намерение в журнал перед каждым изменяющим запросом и дублирует изменения в новое хранилище, а утилита массового переноса копирует накопленные объекты.

Постановка: [docs/problem-and-tasks.md](docs/problem-and-tasks.md). План работ по задачам: [tasks/README.md](tasks/README.md).

## Runbook миграции

Два параллельных процесса (журнал изменений и массовый перенос), как они стыкуются, порядок запуска и все шаги на серверах описаны в [PIPELINE.md](PIPELINE.md):

1. **Этап A, сейчас, без нового S3:** шлюз в рабочем пути, подтверждение охвата журнала, инвентаризация бакета.
2. **Этап B, когда новое S3 развёрнуто ([задача 03](tasks/03-deploy-new-storage.md)):** обработчик разбирает журнал, перенос копирует по готовому листингу.
3. **Этап C:** проверка полноты, переключение шлюза на новое S3 на `minio2`, откат при необходимости.

## Структура

```
s3gw/          шлюз, журнал намерений и массовый перенос (текущая миграция)
migrator/      сверка бакетов для C1 (reconcile_buckets.py, фаза verify)
scripts/       окно переключения и откат (cutover.sh), сверка st5, стенды в Docker, замеры задержки шлюза и SQLite на 12 млн ключей, проверка нового S3
deploy/        nginx для включения шлюза на minio2 и прокси C5 на новом сервере; systemd-юниты s3gw (шлюз, бэкап журнала, обработчик, перенос); SeaweedFS и nginx с TLS на ВМ нового S3
docs/          актуальные техописания (шлюз, перенос, маршрутизация, откат, паспорт источника)
docs/tools/    документация к сверке C1
tasks/         задачи 01–13 текущей миграции
tests/         pytest
```

Состояние запусков (SQLite, логи, спулы) скрипты пишут в `.runtime/`, он тоже не в git.

Код прошлой миграции, который новой схеме не нужен (Stage 1–3, Kafka-синк, манифесты, проверки по ELMA365 Stage 4, докопирование), в эту версию репозитория не входит.

## Запуск

Все команды на серверах — в [PIPELINE.md](PIPELINE.md); код ставится в `/opt/elma365_s3_migrator` (раздел A2).

## Тесты

```bash
pip install -r requirements-dev.txt
python3 -m pytest
```

Стенд всего [PIPELINE.md](PIPELINE.md) от A до C в Docker (MinIO и `mc` версий `minio2`, nginx 1.28, SeaweedFS 4.48 как новое S3): `python scripts/stand_pipeline.py`, ~17 минут. Прогонять перед выкладкой изменений.

Стенд прерываний процесса журнала на той же реплике: `python scripts/stand_journal_recovery.py`, ~12 минут. В нём одновременное падение всех процессов, `kill -9` и `systemctl restart` шлюза под нагрузкой, падение обработчика посреди multipart, заполненный диск журнала и восстановление журнала из копии (A5) со сверкой C1. Прогонять после изменений шлюза, журнала и обработчика.

Стенд runbook: `python scripts/stand_runbook.py`, ~6 минут; первый запуск дольше, он собирает образ. Bash-блоки [PIPELINE.md](PIPELINE.md) от A0 до C4 выполняются дословно, от root, в одной сессии оператора. Реплика `minio2` поднята на systemd: MinIO как сервис с `/etc/default/minio`, nginx 1.28, юниты из `deploy/`. Окно C2/C4 проходит через `scripts/cutover.sh`. Каждая замена в блоке (плейсхолдеры, `vi`, укороченные ожидания) пишется в отчёт с причиной. Стенд проверяет и прерывания: листинг A7 останавливается и запускается снова, сверка C1 убивается посреди работы и продолжается с `RESUME=1`, а `switch`, `undo` и `rollback` убиваются после каждого шага по очереди и доводятся до конца повторным запуском. `minio2` перезагружается посреди листинга A7, в окне C2 после `switch` и теряет питание посреди копирования B1, причём MinIO поднимается последним. Журнал на этапе A теряется и восстанавливается из копии по A5. С `--soak 3` перед этапом C идёт три часа трафика: память шлюза и обработчика, WAL при постоянных читателях, ротация копий настоящим часовым таймером. Прогонять после правок PIPELINE.md, юнитов, конфига nginx и `cutover.sh`. С `--keep` реплика остаётся для ручной репетиции (C0.4). Контейнер привилегированный: так systemd работает в Docker.

Стенд прокси C5: `python scripts/stand_c5.py`, ~1 минута. Старый MinIO, SeaweedFS и nginx с [deploy/nginx/s3-c5.conf](deploy/nginx/s3-c5.conf): чтение объекта, которого нет в новом S3, уходит в старый MinIO и пишется в лог, остальное идёт только в новое S3.

Замер SQLite на объёме миграции: `python scripts/bench_journal_scale.py`, ~10 минут. Журнал и `bulk.db` по 12 млн ключей, время удержания блокировки записи у каждой операции, ожидание шлюза под общей нагрузкой, копия журнала, `tracecheck`, продолжение сверки C1. Прогонять после изменений запросов к журналу и `bulk.db`.
