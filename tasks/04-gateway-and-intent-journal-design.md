# Задача 04. Техописание шлюза и журнала намерений

Раздел постановки: 5, 5.1, 5.3, 8; 7, задача 4.
Зависит от: 01 (перечень операций и источников изменений).
Блокирует: 05, 06, 07, 12.

## Цель

Описать шлюз за nginx, который до передачи изменяющего запроса в старый MinIO надёжно фиксирует намерение изменить ключ, а также обработчик, который приводит ключ в новом S3 к текущему состоянию MinIO. Описание должно быть достаточным для реализации и испытаний в задаче 06.

## Контекст

- До переключения MinIO — основной: ELMA365 читает из него, он определяет актуальное состояние.
- Новое S3 обновляется асинхронно. Недоступность приёмника приводит к накоплению заданий, а не к остановке ELMA365.
- Kafka-подход прошлой миграции (`migrator/event_sync.py`) узнавал об изменении *после* факта и терял события. Журнал намерений должен устранить именно этот класс проблем: если запись в журнал не удалась, запрос в MinIO не уходит.
- Отсутствие S3-версий не означает отсутствия перезаписи ключей.

## Что описать

### Операции
- [ ] Перечень изменяющих операций, которые шлюз разбирает (по итогам задачи 01): PutObject, CopyObject (ключ-приёмник), multipart (Create/UploadPart/UploadPartCopy/Complete/Abort), DeleteObject, DeleteObjects, PutObjectTagging/DeleteObjectTagging и т. п.
- [ ] Чтения (GET/HEAD/List) проксируются в MinIO без записи в журнал.
- [ ] Поведение для неизвестных/неподдерживаемых изменяющих операций: отказ клиенту или журналирование «грязного» ключа/префикса. Выбрать и обосновать.

### Порядок фиксации
- [ ] Шаг 1: записать намерение (ключ, операция, время, внутренний счётчик изменений) в постоянный журнал с подтверждённым fsync.
- [ ] Шаг 2: передать запрос в MinIO.
- [ ] Шаг 3: записать результат: успех, ошибка, **неопределённо** (тайм-аут, разрыв).
- [ ] Шаг 4: вернуть клиенту исходный ответ MinIO без изменений.
- [ ] Если шаг 1 невозможен (журнал недоступен, диск заполнен): запрос не передаётся, клиент получает ошибку 503/SlowDown. Зафиксировать это как осознанный компромисс доступности.

### Состояние и обработчик
- [ ] Модель данных: таблица ключей с полями `key`, `change_seq`, `synced_seq`, `state`, `in_flight`, `attempts`, `last_error`, `updated_at`; таблица намерений; таблица ошибок.
- [ ] Состояния ключа (например: `dirty` → `syncing` → `synced` / `deleted` / `error` / `uncertain`).
- [ ] Обработчик не повторяет HTTP-запрос, а читает текущий объект из MinIO (HEAD + GET) и записывает его в новое S3; если в MinIO объекта нет по достоверному `404 NoSuchKey`, удаляет его в новом S3.
- [ ] Ключ считается синхронизированным, только если за время обработки `change_seq` не изменился и нет незавершённых операций (`in_flight = 0`).
- [ ] Блокировка по ключу между обработчиком текущих изменений и массовым переносом (задача 05). Описать алгоритм и доказать на сценариях, что массовый перенос не перезапишет новое содержимое старым и не вернёт удалённый объект.
- [ ] Восстановление после сбоя шлюза: все намерения без результата перепроверяются по источнику; без достоверного результата не объявляются выполненными.

### Multipart
- [ ] Клиентская сессия идёт только в MinIO. Намерение фиксируется на CreateMultipartUpload и на CompleteMultipartUpload; после успешного Complete ключ ставится в очередь как обычный PUT.
- [ ] Незавершённые и неопределённые Complete после сбоя: как обнаруживаются (ListMultipartUploads в MinIO, HEAD ключа) и когда закрываются.

### Пакетное удаление
- [ ] Журналировать все ключи из тела DeleteObjects до передачи запроса.
- [ ] Разбирать ответ по каждому ключу. Ошибки доступа, отсутствие бакета, сетевые ошибки не трактуются как «объекта нет» и не ведут к удалению в новом S3.

### Безопасность и корректность ключей
- [ ] Ключи хранятся в журнале в исходном виде (байты/UTF-8), без `unquote_plus` и нормализации регистра.
- [ ] Подпись SigV4: шлюз либо проксирует запрос неизменным (тогда он не должен менять тело, заголовки, путь), либо переподписывает своими ключами. Выбрать.
- [ ] Отдельные ключи доступа шлюза/обработчика к новому S3; секреты не попадают в журнал.

### Отказы
- [ ] Недоступность журнала, заполнение диска, недоступность MinIO, недоступность приёмника, частичные ошибки S3. Для каждого: что видит ELMA365, что происходит с очередью, как восстановиться.
- [ ] Изменения, которые не проходят через шлюз (lifecycle MinIO, админы с `mc`, другие сервисы): запретить, перенаправить через шлюз или ловить сверкой (задача 10).

### Технологии
- [ ] Язык реализации, S3-библиотека, база состояния. Ориентир: проект написан на Python 3 + boto3 + SQLite (WAL). Для шлюза с одновременной записью из многих соединений проверить, хватает ли SQLite, или нужен PostgreSQL. Решение записать с замером.
- [ ] Место размещения шлюза и журнала, защита их диска.

## Риски по времени

- Ошибка в алгоритме блокировок обнаружится только при сверке после переноса и приведёт к повторной полной сверке. Поэтому алгоритм проверяется на сценариях на бумаге до реализации.
