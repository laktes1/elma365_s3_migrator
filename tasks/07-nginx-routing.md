# Задача 07. Конфигурация nginx и маршрутизации

Раздел постановки: 5, 6; 7, задача 7.
Зависит от: 04, 06.
Блокирует: 08.

## Цель

Подготовить входную точку S3 для ELMA365: nginx принимает все запросы и отдаёт изменяющие в шлюз, сохраняя корректность подписей, адресации и больших файлов, без обхода шлюза и без `nginx mirror`.

## Контекст

- `nginx mirror` не даёт подтверждённой второй записи, очереди и корректного дублирования multipart. Не используется.
- Есть прошлая конфигурация fallback `/etc/nginx/conf.d/minio-migration.conf` (новое → при 404 старое, удаления запрещены). Это **альтернативная** архитектура, не основа текущей. Исторические адреса: новое S3 `127.0.0.1:9000`, старое `10.10.0.7:9000`, nginx `10.10.0.12:8083`; их актуальность не подтверждена.

## Что сделать

- [ ] Решить схему: весь S3-трафик идёт в шлюз (шлюз сам проксирует чтения в MinIO) или nginx разделяет чтения и изменения по методу и параметрам запроса. Первый вариант проще и не даёт ошибиться в классификации; второй снижает нагрузку на шлюз. Решение согласовать с задачей 04.
- [ ] Сохранить для SigV4: `Host`, путь без перекодирования (`proxy_pass` без URI-части, внимательно к `merge_slashes`), строку запроса, заголовки `x-amz-*`, `Content-MD5`, `Expect: 100-continue`.
- [ ] Адресация бакета (path-style / virtual-host) как в текущем подключении ELMA365.
- [ ] `client_max_body_size 0`, `proxy_request_buffering off`, `proxy_buffering off` для больших файлов; тайм-ауты чтения/записи под объекты > 512 МБ (193 объекта по снимку).
- [ ] Range и HEAD, presigned URL (проверить, что подпись в ссылке совпадает с хостом, по которому идёт пользователь).
- [ ] TLS, если ELMA365 подключается по https.
- [ ] Закрыть прямой доступ к MinIO для всех изменяющих клиентов (firewall/сетевые правила), оставив его только шлюзу и администраторам по процедуре. Список клиентов — из задачи 01.
- [ ] Сохранить текущую конфигурацию и описать возврат маршрутизации на прямой MinIO до начала записи в новое S3.
- [ ] Проверить конфигурацию на стенде задачи 06 полным набором операций, включая подписанные ссылки и multipart.

## Риски по времени

- Ошибка в проксировании подписей проявится только на части запросов (ключи со спецсимволами, presigned URL). Тестировать на ключах из `bad-keys.txt` и с `+`/пробелами.

## Результат

Проверенная конфигурация nginx, описание изменений сетевого доступа к MinIO, процедура возврата маршрутизации.

## Решения

- 2026-10-21. Шлюз включается nginx на самом `minio2`, Kubernetes/ingress/haproxy не меняются: nginx слушает `10.10.0.12:9000`, MinIO переводится на `127.0.0.1:9000`, шлюз на `127.0.0.1:9100`. Разделение по методу: чтения `s3elma365` и все запросы к другим бакетам идут прямо в MinIO, изменения `s3elma365` в шлюз. Вариант с haproxy в Kubernetes удалён. Описание: [docs/nginx-routing.md](../docs/nginx-routing.md), конфиг: [deploy/nginx/s3gw.conf](../deploy/nginx/s3gw.conf).
- 2026-10-21. Прямой доступ к MinIO закрыт тем, что MinIO слушает только loopback; firewall не нужен.
- 2026-10-21. Охват проверяется по метке `X-S3gw-Request-Id`, которую шлюз добавляет к пересылаемым запросам: по IP нельзя, MinIO показывает в трассировке `X-Forwarded-For` от ingress. Проверено на локальном стенде (`scripts/stand_journal_only.py`) с MinIO `2025-09-07` и `mc` `2025-08-13`. С 2026-10-22 это шаг A6 `scripts/stand_pipeline.py`.
- 2026-10-22. Окончательно: работаем через nginx на `minio2`, без Kubernetes и его конфига. Вариант с правилами iptables (весь `:9000` в шлюз) удалён. При переключении на новое S3 (PIPELINE.md, C2) чтения `s3elma365` в `map` nginx тоже переводятся в шлюз.
