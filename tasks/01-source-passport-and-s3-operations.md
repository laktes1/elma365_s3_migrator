# Задача 01. Паспорт исходной системы и набор S3-операций ELMA365

Раздел постановки: 7, задача 1; раздел 10.
Зависит от: —
Блокирует: 02, 04, 05 (и косвенно всё остальное).

## Цель

Получить факты, без которых нельзя ни выбрать хранилище, ни описать шлюз, ни оценить сроки: версии, объём, операции, источники изменений и реальную скорость листинга старого MinIO.

## Контекст

- Сейчас известны только количество объектов по размерам (12 187 195 на снимок) и физическая занятость дисков (~12,4 ТиБ с учётом EC:2). Логический объём бакета не известен.
- Неизвестно, перезаписывает ли ELMA365 существующие ключи, использует ли multipart, CopyObject, пакетное удаление, теги.
- Прошлая миграция: перечисление/сравнение занимало больше суток, причина не разобрана. Без этого невозможно планировать задачу 09.

## Что сделать

### Паспорт
- [ ] Версии ELMA365, MinIO (`mc admin info`), используемых S3-клиентов/SDK внутри ELMA365.
- [ ] Имя бакета (в конфигах проекта по умолчанию `s3elma365`, подтвердить), endpoint, region, path-style или virtual-host адресация, TLS.
- [ ] Способы авторизации: ключи доступа, SigV4/SigV2, presigned URL (кто их генерирует и кто по ним ходит: браузер пользователя или сервисы).
- [ ] Логический объём бакета: `mc du` по префиксам или сумма размеров при листинге из задачи «Замер листинга» ниже.
- [ ] Устройство EC-наборов MinIO (`mc admin info`, число erasure sets и дисков в наборе).
- [ ] Полоса и задержка канала облако → физический сервер (iperf3 или аналог в обе стороны, в рабочее и ночное время).

### Операции ELMA365
- [ ] Включить на время наблюдения журнал запросов MinIO (`mc admin trace` с фильтрацией по бакету, либо audit webhook) **без записи тел и секретов** и собрать статистику по типам API за несколько рабочих дней, включая ночные задания.
- [ ] По статистике определить: PutObject, multipart (Create/UploadPart/Complete/Abort), UploadPartCopy, CopyObject, DeleteObject, DeleteObjects, листинг, Get/Put ObjectTagging, метаданные `x-amz-meta-*`, Range-запросы.
- [ ] Проверить, бывают ли повторные PUT в один ключ (по журналу: один ключ, несколько PUT).
- [ ] Посмотреть формат ключей: по Stage 4 S3-ключ = `file.hash` в ELMA365 (UUID-подобный), `scripts/manifester.sh` раскладывает по первым двум hex-символам. Проверить, есть ли ключи с `/`, пробелами, `+`, кириллицей (файл `bad-keys.txt` от прошлого запуска, если сохранился).

### Источники изменений
- [ ] ELMA365 (все сервисы, которые ходят в S3), интеграции, администраторы с `mc`, фоновые задания, lifecycle-правила MinIO (`mc ilm rule ls`), уведомления (`mc event ls`; от прошлой миграции могла остаться Kafka-нотификация).
- [ ] Для каждого источника: проходит ли он через будущий шлюз и как это обеспечить (вход для задач 04 и 07).

### Замер листинга и разбор прошлой медленности
- [ ] Найти логи прошлой миграции: `build-manifests.log`, `.runtime/st5-reconcile/progress.jsonl`, отчёты `benchmark` Stage 5, логи `migrator/find_delta.py`.
- [x] Замер листинга не делается (решение ниже): скорость источника покажет начало A7 (`page_ms_last_5m`). Фаза `benchmark` сверки удалена 2026-10-22.
- [ ] Отдельно замерить скорость GET мелких объектов (1–256 КБ) с разной параллельностью. Это главный ограничитель задачи 09.
- [ ] Сформулировать, что тормозило: сам ListObjects, HEAD на каждый объект, или логика инструмента (например, полный `mc find` в один поток).

## Риски по времени

- Сбор статистики операций требует нескольких рабочих дней наблюдения. Начать сразу, параллельно с остальной частью паспорта.
- Тяжёлый `mc admin trace` сам нагружает MinIO; ограничить фильтром и временем.

## Результат

Файл `docs/source-passport.md` (или раздел «Решения» ниже) с паспортом, перечнем обязательных S3-операций с частотой, списком источников изменений, измеренной скоростью листинга и GET и выводом о причине прошлой медленности.
