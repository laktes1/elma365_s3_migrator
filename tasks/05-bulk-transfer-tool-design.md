# Задача 05. Техописание утилиты массового переноса

Раздел постановки: 5.2, 5.3, 8; 7, задача 5.
Зависит от: 01 (замеры листинга и GET), 04 (общая база состояния и блокировки).
Блокирует: 06, 09.

## Цель

Описать утилиту, которая один раз перечисляет старый бакет с контрольными точками и переносит накопленные объекты в новое S3, согласуясь с обработчиком текущих изменений и не мешая работе ELMA365.

## Контекст

- 12,2 млн объектов, 87,5% меньше 1 МБ. Узкое место — случайное чтение на HDD старого MinIO, а не сеть.
- В прошлый раз полный листинг выполнялся несколько раз и занимал больше суток каждый. Утилита должна перечислить бакет **один раз** и уметь продолжить с места остановки.
- Всё содержимое и весь список не загружаются в память ВМ (бюджет 16 ГБ).

## Что описать

### Перечисление
- [ ] Разбиение на разделы по префиксу ключа (как `PREFIX_LEN=2` в Stage 5: `00..ff` + catch-all для не-hex ключей). Подтвердить по задаче 01, что распределение ключей по префиксам равномерное.
- [ ] Контрольная точка перечисления: для каждого раздела хранится последний полученный `StartAfter`/`ContinuationToken` и статус. После сбоя листинг раздела продолжается с последней точки, а не с начала.
- [ ] Запись страницы листинга в базу заданий и обновление контрольной точки в одной транзакции.
- [ ] Формат записи задания: `key`, `size`, `etag`, `last_modified` из листинга, `state`, `attempts`, `last_error`, `checked_at`.
- [ ] Параллельность листинга по разделам и размер страницы задаются по замерам задачи 01 (в прошлый раз для источника требовались `PageSize=100` и тайм-аут 900 с).

### Перенос
- [ ] Несколько обработчиков берут задания из базы. Перед записью ключа берётся блокировка из задачи 04; если ключ «грязный» по журналу намерений, задание отдаётся обработчику текущих изменений или откладывается.
- [ ] Чтение из MinIO потоком, без буферизации объекта в памяти целиком; большие объекты — multipart в приёмник.
- [ ] Перенос метаданных: `Content-Type`, `x-amz-meta-*`, `Content-Disposition`, `Content-Encoding`, `Cache-Control`, теги (если используются по задаче 01).
- [ ] Проверка после записи: минимум размер по HEAD приёмника; способ проверки содержимого выбирается в задаче 10 (ETag не всегда MD5, особенно для multipart).
- [ ] Повторные попытки с экспоненциальной задержкой, лимит попыток, перевод в `error` с причиной. Достоверный `404` в источнике → `source_missing`, без удаления в приёмнике силами массового переноса.

### Управление нагрузкой
- [ ] Расписание с явным часовым поясом (например, `Europe/Moscow`): дневной и ночной лимит потоков и полосы.
- [ ] Ручное управление без перезапуска: пауза, изменение лимитов (файл управления или таблица в базе).
- [ ] Автоматическое замедление при росте задержек MinIO (по времени ответа GET/HEAD) и при росте отставания очереди текущих изменений. Текущие изменения всегда имеют приоритет.

### Наблюдаемость
- [ ] Периодический отчёт: разделы перечислены/всего, задания по состояниям, объектов/с и байт/с, ETA, отставание журнала.
- [ ] Экспорт нерешённых ошибок в CSV/JSONL.
- [ ] Вторичный проход по ключам, изменённым во время массового переноса (по журналу намерений).

## Риски по времени

- Каждый лишний HEAD на объект — это +12 млн запросов к HDD. Брать размер и ETag из листинга, а HEAD делать только на приёмнике.
- Отсутствие контрольной точки внутри раздела приводит к повторному листингу после каждого сбоя. В прошлой миграции это одна из причин длительности.
