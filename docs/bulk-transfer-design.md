# Утилита массового переноса: техническое описание

Задача: [`tasks/05-bulk-transfer-tool-design.md`](../tasks/05-bulk-transfer-tool-design.md).
Опирается на [`docs/gateway-design.md`](gateway-design.md) (журнал, `key_state`, аренда ключа).
Статус: описывает код в `main` (сверено ревью 2026-10-22). Копирование, нагрузка, команды и отчёты описаны в PIPELINE.md (этап B) и в `s3gw/bulk.py`; согласование с журналом — в `gateway-design.md`, раздел 6.

## 1. Что делает утилита

Один раз перечисляет старый бакет с контрольными точками и переносит в новое S3 те ключи, которые ещё не прошли через журнал шлюза. Перечисление и перенос идут одновременно: раздел можно переносить, как только его первые страницы сохранены.

Утилита запускается **только после** включения шлюза (задача 08). Тогда любое изменение ключа попадает либо в листинг (случилось до перечисления этого места), либо в журнал (случилось после включения шлюза), и ни одно не теряется.

Приёмник в начале пустой. Листинг приёмника для переноса не нужен: всё состояние в базах.

## 2. Найденные дефекты прошлых инструментов, которые учтены

1. **Раздел catch-all в Stage 5 и `migrator/find_delta.py` листил весь бакет.** Для ключей, не попавших в префиксы `00..ff`, листинг шёл без `Prefix` по всему бакету с фильтрацией на клиенте. То есть каждый полный проход Stage 5 содержал ещё один полный листинг источника и приёмника. Это одна из вероятных причин «больше суток на перечисление». В сверке C1 (`reconcile_buckets.py verify`) исправлено 2026-10-22: catch-all листит только 33 промежутка между hex-префиксами.
2. **Ключи, начинающиеся с заглавных hex-символов (`AB…`), пропускались.** Catch-all отбрасывал ключ, если `key[:2].lower()` был hex, а префиксный листинг `Prefix="ab"` чувствителен к регистру и такой ключ не возвращает. Исправлено в этой ветке (оба файла, тесты). Если в бакете есть такие ключи, прошлая сверка их не видела.
3. **Нет контрольной точки внутри раздела в Stage 5**: раздел после сбоя листился заново целиком.
4. **Переносился только `Content-Type`** (`copy_one_object`), пользовательские метаданные и теги терялись.

Новая утилита делит бакет **по диапазонам ключей**, а не по префиксам. Это убирает и catch-all, и вопрос регистра: каждый ключ попадает ровно в один диапазон по побайтовому порядку S3.

## 3. База заданий (`bulk.db`)

Отдельный файл SQLite WAL рядом с `journal.db` (та же ВМ, локальный диск). Отдельный файл нужен, чтобы 12 млн вставок листинга не держали блокировку записи журнала шлюза.

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;   -- потеря последней транзакции при сбое ОС безопасна: страница листинга перечитается

CREATE TABLE ranges (
  id           INTEGER PRIMARY KEY,
  lo           TEXT NOT NULL,          -- включительно ('' для первого)
  hi           TEXT,                   -- не включительно (NULL для последнего)
  status       TEXT NOT NULL,          -- pending | listing | listed | error
  start_after  TEXT,                   -- контрольная точка: последний сохранённый ключ
  listed_count INTEGER NOT NULL DEFAULT 0,
  listed_bytes INTEGER NOT NULL DEFAULT 0,
  pages        INTEGER NOT NULL DEFAULT 0,
  last_error   TEXT,
  started_at   TEXT,
  finished_at  TEXT,
  updated_at   TEXT NOT NULL
);

CREATE TABLE jobs (
  key           TEXT PRIMARY KEY,
  range_id      INTEGER NOT NULL,
  size          INTEGER NOT NULL,      -- из листинга
  etag          TEXT,                  -- из листинга, без кавычек
  last_modified TEXT,
  state         TEXT NOT NULL,         -- pending | claimed | done | skipped_journal | source_missing | retry | error
  owner         TEXT,
  claim_until   TEXT,
  attempts      INTEGER NOT NULL DEFAULT 0,
  not_before    TEXT,
  last_error    TEXT,
  verify        TEXT,                  -- size | md5 (каким способом проверено)
  updated_at    TEXT NOT NULL
);
CREATE INDEX idx_jobs_work ON jobs (state, range_id) WHERE state IN ('pending', 'retry');

CREATE TABLE control (                 -- ручное управление без перезапуска ($B pause / resume / set)
  name  TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

Размер: около 200 байт на задание с индексом, то есть 2,5–3 ГБ на 12,2 млн ключей. В память база не загружается.

## 4. Перечисление

### Диапазоны

По умолчанию 257 диапазонов: `['', '01')`, `['01', '02')`, …, `['fe', 'ff')`, `['ff', ∞)`. Граница — строка, сравнение побайтовое, как у S3. Ключи с заглавными буквами, кириллицей и прочим попадают в диапазоны по порядку байтов, ничего не теряется и ничего не листится дважды. Если задача 01 покажет неравномерное распределение (например, все ключи с одной буквы), границы задаются файлом `--ranges-file`.

### Листинг диапазона

```
StartAfter = ranges.start_after или pred(lo), если lo != ''
Prefix     = общий префикс lo и hi (для '0a'..'0b' это '0'), чтобы MinIO не обходил лишнее
повторять:
    ListObjectsV2(Bucket, Prefix, StartAfter, MaxKeys = LIST_PAGE_SIZE)
    оставить ключи с lo <= key < hi
    BEGIN
      INSERT OR IGNORE INTO jobs (key, range_id, size, etag, last_modified, state='pending')
      UPDATE ranges SET start_after = последний ключ страницы, listed_count += n, pages += 1
    COMMIT
    если ключ >= hi или страница последняя: ranges.status = 'listed'
```

- `pred(lo)` — строка-предшественник: `lo` с последним символом, уменьшенным на 1, дополненная символами U+10FFFF и в конце U+07FF до 1024 байт UTF-8. Между `pred(lo)` и `lo` нет ни одного допустимого ключа S3 (ключ не длиннее 1024 байт), поэтому листинг начинается ровно с `lo` и не обходит предыдущий диапазон. Функция и её тест — в задаче 06; там же проверить, что MinIO принимает такой `StartAfter`.
- Контрольная точка — `StartAfter` по последнему сохранённому ключу: токен MinIO непрозрачен и не обязан переживать перезапуск. Внутри прогона следующие страницы запрашиваются по `NextContinuationToken`: страницу только со `StartAfter` MinIO обслуживает новым обходом плоского каталога бакета, и на стенде её цена росла с размером бакета (50 → 100 → 150 мс на 20 / 100 / 300 тыс. объектов), а с токеном нет (53 → 67 → 69 мс). После ошибки запроса и после перезапуска листинг продолжается со `StartAfter`.
- Страница и контрольная точка сохраняются **в одной транзакции**. После сбоя листинг продолжается со следующего ключа; повторно сохранённая страница безвредна (`INSERT OR IGNORE`).
- `LIST_PAGE_SIZE` и число одновременно листящихся диапазонов `LIST_WORKERS` — по замеру задачи 01. В прошлый раз для источника понадобились `PageSize=100` и тайм-аут чтения 900 с; если это подтвердится, лучше больше параллельных диапазонов с маленькой страницей, чем одна большая страница.
- Повторы страницы: экспоненциальная задержка, после `BULK_MAX_ATTEMPTS` диапазон уходит в `error` с сохранённой точкой, остальные продолжают. Команда `retry-errors` возвращает их в работу.
- Листинг с `Delimiter` не используется: нужны все ключи, включая содержащие `/`.
- Вопрос к задаче 01: если ключи плоские (без `/`), MinIO хранит все 12 млн объектов как каталоги в одном каталоге бакета на каждом диске, и любой листинг, даже по префиксу, может упираться в чтение этого каталога. Тогда параллельный листинг по диапазонам не ускорит перечисление, и выгоднее один-два потока с большой страницей. Это видно по `page_ms_last_5m` в первый час A7 (PIPELINE.md).

## 5. Завершение

Массовый перенос закончен, когда все диапазоны `listed`, а заданий в `pending`, `claimed`, `retry` нет. Задания в `error` и `source_missing` перечислены в отчёте. Отдельный повторный проход по изменённым ключам не нужен: они в `key_state` и закрываются обработчиком (см. `gateway-design.md`, конец раздела 6). Полнота и содержимое проверяются в задаче 10.
