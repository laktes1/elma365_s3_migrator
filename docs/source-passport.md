## Остатки прошлой миграции на `minio2` (2026-10-21)

На `minio2` работает nginx с `/etc/nginx/conf.d/minio-migration.conf` (`listen 10.10.0.12:8083`): это конфигурация fallback из раздела 6 постановки. Сейчас haproxy смотрит мимо него, на `:9000`.

Поведение этой конфигурации и его следствия для прошлой миграции:

- `DELETE` объекта и `POST ?delete` отклонялись с `405` (отмена multipart с `uploadId` разрешалась). ELMA365 получала ошибку удаления, объект оставался в обоих MinIO.
- `GET`/`HEAD`: сначала новый MinIO, при `404` старый (`10.10.0.7:9000`).
- Все изменения, включая `CopyObject` и `UploadPartCopy`, шли только в новый MinIO. Если источник копирования ещё не был перенесён, копирование падало с `404`: это вероятный механизм ошибок ELMA365 в тот период.
- `proxy_set_header Host $http_host`, `proxy_request_buffering off`, тайм-ауты 3600 с — те же требования переносятся в конфиг шлюза.
- JSON-логи: `minio-migration.json` (все запросы, кроме заблокированных удалений), `minio-old-hit.json`, `minio-both-missing.json`. Пишется `$uri` без строки запроса. Если логи сохранились, из них получается статистика методов ELMA365 без `mc admin trace`.

Выводы:

- **За две недели ни одного `POST`**: multipart-загрузки (`POST ?uploads`, `POST ?uploadId`) не использовались. Пакетное удаление (`POST ?delete`) по этому логу не видно: такие запросы отклонялись и, по конфигу, в основной лог не писались. Проверить по логам ingress или `mc admin trace`.
- Запись: около 115 тыс. PUT за 14 дней, то есть ~8 тыс. в сутки, в среднем 0,1 в секунду. Для журнала на SQLite это ничтожная нагрузка.
- Удаления: ~800 в сутки. В прошлую миграцию все они получили `405`, и файлы, которые ELMA365 пыталась удалить, остались в хранилище.
- **Перезапись ключей есть, но редкая**: 18 ключей получили больше одного успешного PUT за две недели. Значит, журнал обязан учитывать перезапись, а сверка «ключ + размер» без журнала её пропустила бы.
- **61 разный ключ ELMA365 запрашивала, а его не было ни в одном MinIO** (`minio-both-missing.json`). Это кандидаты на файлы, потерянные в прошлой миграции (или удалённые законно). По решению владельца (2026-10-21) прошлое не расследуется.
- Повторных DELETE одного ключа в логе нет (но заблокированные удаления после смены конфига в лог не писались).
- Со слов владельца: удаления отключили, потому что запросы DELETE с ответом `405` за короткое время дали 35 ГБ журнала; после отключения прокси ELMA365 дочищала накопленные удаления, и это дало большую нагрузку на MinIO. Значит, ELMA365 повторяет неудавшиеся удаления. Требования к шлюзу: удаления не блокировать; не писать текстовый лог на каждый запрос (шлюз и так работает без access log); строки `intents` чистить по сроку хранения; групповая фиксация в журнале на случай волны удалений.
- CopyObject и теги по этому логу неотличимы от обычного PUT (нет заголовков и строки запроса).
- Чтение доминирует (GET+HEAD ≈ 87%), поэтому разделение по методу и прямой путь чтений в MinIO снимают с шлюза почти всю нагрузку.

## Выводы для шлюза и маршрутизации

1. **Точка включения шлюза — haproxy, а не отдельный nginx.** В `backend`/`frontend` haproxy добавляется разделение по методу: `GET`/`HEAD` в MinIO, `PUT`/`POST`/`DELETE` в шлюз. Это изменение `values-s3gateway.yaml` и `helm upgrade`, а возврат — прежние values. Задача 07 переформулируется под haproxy.
2. **`Host` должен доходить до MinIO неизменным** (`elma.example.com`): подписанные ссылки подписаны с `SignedHeaders=host`. Сейчас это так работает через ingress и haproxy, и прозрачный шлюз это сохраняет.
3. **Ключи плоские.** MinIO хранит все объекты как каталоги в корне бакета, поэтому листинг по префиксу, вероятно, не быстрее полного. Проверяется замером (блок Г).
4. **Тайм-ауты haproxy 60 с.** Для загрузок больших файлов через шлюз они остаются прежними: шлюз не должен их сокращать.
5. ELMA365 обращается к S3 через `elma.example.com`, поэтому шлюз в haproxy охватывает весь трафик, а статистику операций можно брать из логов ingress-nginx или старого JSON-лога nginx на `minio2`.
