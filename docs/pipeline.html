Конвейер миграции s3elma365: MinIO → новое S3

Два процесса работают параллельно на minio2 (10.10.0.12) рядом с MinIO и делят одну базу состояния ключей journal.db. Журнал ловит каждое изменение ELMA365 и приводит ключ в новом S3 к текущему состоянию MinIO. Перенос перечисляет весь бакет и копирует то, чего журнал не касался.

процесс 1: журнал изменений процесс 2: перенос чтения и другие бакеты, без журнала работа с базой SQLite служебное: бэкап, проверка

Схема на этапах A и B

Наведите курсор на компонент, чтобы подсветить его связи. Щелчок открывает описание ниже. Стрелки показывают, кто делает запрос.

Компоненты

nginx

вход
deploy/nginx/s3gw.conf → /etc/nginx/conf.d/s3gw.conf
  • 10.10.0.12:9000 принимает весь трафик вместо MinIO; служебный порт 127.0.0.1:9080 для проверки (A3).
  • Выбор по методу: GET, HEAD, OPTIONS к s3elma365 идут в MinIO, всё остальное к s3elma365 идёт в шлюз, другие бакеты всегда в MinIO.
  • proxy_next_upstream off, запасного пути нет: шлюз лежит → 502, журнал недоступен → 503.
  • Host, путь и заголовки уходят как пришли, подписи SigV4 не ломаются; тела не буферизуются, тайм-аут 3600 с.
  • Лог только 5xx: /var/log/nginx/s3gw-5xx.log.
  • Откат до C2: default s3gw_minio и reload. После C2 чтения s3elma365 тоже идут в шлюз.

s3gw-gateway

процесс 1 · шлюз
127.0.0.1:9100 · s3gw/gateway.py
  • ① Намерение: строка в intents, в key_state change_seq + 1, in_flight + 1, state = dirty. COMMIT с fsync до отправки в MinIO.
  • Не записалось за GW_JOURNAL_TIMEOUT = 2 с → 503 SlowDown, в MinIO ничего не ушло.
  • ② Запрос в MinIO байт в байт, тело потоком, плюс X-S3gw-Request-Id (присланный клиентом срезается).
  • ③ Результат success / error / uncertain, снова change_seq + 1, in_flight − 1. Ответ MinIO клиенту без изменений.
  • DeleteObjects: намерение на каждый ключ из тела, одной транзакцией.
  • Операции над бакетом → 501. Другие бакеты → GW_OTHER_UPSTREAM без журнала.
  • Файл read-only → 503 на изменения (окно C2). Рестарт: новая эпоха, незакрытые намерения → uncertain.

journal.db

общая база
/var/lib/s3gw/journal.db · s3gw/journal.py
  • intents: каждое изменение: ключ, операция, результат, id запроса.
  • key_state: состояние ключа, change_seq / synced_seq, in_flight, аренда, попытки, последняя ошибка.
  • mpu: multipart-сессии. gateway_epochs: запуски шлюза. errors, counters.
  • Отставание: ключи в dirty, uncertain, syncing, bulk, у которых не synced_seq = change_seq и in_flight = 0.
  • Бэкап: s3gw-journal-backup.timer раз в час в /backup/s3gw через VACUUM INTO, хранятся 2 копии (A5).
  • Читать только sqlite3 -readonly от пользователя s3gw. Около 6 ГБ на 12 млн ключей вместе с bulk.db.

s3gw-handler

процесс 1 · обработчик
s3gw/handler.py · HANDLER_WORKERS=4 · GW_LEASE_SECONDS=900
  • Берёт ключ dirty или uncertain с in_flight = 0 и not_before ≤ now, ставит аренду и syncing, запоминает change_seq.
  • Один GET из MinIO: тело и метаданные одной версии. NoSuchKey → DELETE в новом S3.
  • Запись: до 16 МиБ одним PUT, крупнее multipart частями по 16 МиБ; Content-*, x-amz-meta-*, теги (запрос тегов только к объектам, у которых GET сообщил TagCount).
  • Проверка: тело сверяется с MD5 из ETag источника и уходит с Content-MD5, приёмник сам отвергнет порчу; затем HEAD сверяет размер.
  • change_seq не изменился → synced / deleted; изменился → снова dirty.
  • Ошибки: повтор через 5 с с удвоением до 600 с, после 20 попыток error.
  • Без DST_* не стартует; включается на этапе B (B1). После C2 работает обратно, новое S3 → MinIO, с journal-reverse.db.

s3gw-bulk

процесс 2 · перенос
python -m s3gw.bulk list | copy | run · s3gw/bulk.py
  • list: ListObjectsV2 по 256 диапазонам 00…ff прямо в 127.0.0.1:9000, мимо nginx. Страница LIST_PAGE_SIZE = 1000, до LIST_WORKERS = 4 листеров. Следующие страницы идут по ContinuationToken, контрольная точка StartAfter сохраняется в одной транзакции со страницей.
  • copy: BULK_WORKERS = 8. Ключ уже в key_state → skipped_journal. Иначе аренда state = bulk, копия тем же copy_key, что у обработчика.
  • После копии: ключ не менялся → synced; менялся → dirty, его доделает обработчик.
  • Лимит = минимум из SCHEDULE (днём 2 потока и 200 Мбит/с, ночью 8 и 800), ручных pause / workers_max / mbps_max и паузы при отставании журнала больше JOURNAL_BACKLOG_MAX = 10 000.
  • run = list + copy; если листинг готов, сразу copy. Код 2: закончил с ошибками заданий; код 3: упал поток, systemd перезапустит через 30 с.

bulk.db

задания переноса
/var/lib/s3gw/bulk.db · bulk-progress.jsonl
  • ranges: pending → listing → listed, после исчерпанных повторов error. Хранит контрольную точку и счётчики.
  • jobs: pending → claimed → done, либо skipped_journal или source_missing; сбой → retry, после 10 попыток error.
  • control: пауза и потолки без перезапуска ($B pause, $B set workers_max 4).
  • Отдельный файл, чтобы 12 млн вставок листинга не держали блокировку журнала шлюза.
  • bulk-progress.jsonl: скорость, ETA, текущий лимит и его причина (schedule, manual, paused, journal_lag).

MinIO

источник
127.0.0.1:9000 после A4 · /etc/default/minio
  • Бакет s3elma365, около 12 млн объектов на 16 HDD. Перенос и обработчик читают объект одним GET; теги отдельным запросом — только если GET сообщил, что они есть.
  • После A4 слушает только loopback: снаружи писать мимо nginx и шлюза нельзя. Писать мимо шлюза могут только процессы на самом minio2.
  • Пользователь s3gw-src только на чтение s3elma365 (A1).
  • elma365-backups, -loki, -tempo в миграцию не входят и не зависят от шлюза.
  • После C2 в s3elma365 пишет только обратный обработчик; MinIO остаётся запасным источником для отката.

Новое S3

приёмник
DST_ENDPOINT · задача 03
  • Бакет s3elma365; ключ DST_* с записью только в этот бакет.
  • Порт открыт только для minio2, поэтому писать в новое S3 можно только через шлюз и обработчик.
  • До переключения принимает ELMA365 с теми же ключами доступа: проверка подписи check_new_s3_signature.py (C0).
  • После C2 основное хранилище: шлюз ходит сюда, журнал и обработчик пишут изменения обратно в MinIO.

Проверки

контроль полноты
s3gw/tracecheck.py · s3gw/verifykeys.py · st5_reconcile_buckets.sh
  • tracecheck (A6): час mc admin trace --verbose. Норма bypass_total = 0, missed_total = 0. Первая чистая проверка разрешает листинг.
  • --mark-dirty: ключи, изменённые мимо шлюза (например, во время отката), отдаются обработчику.
  • Сверка (C1): заново листит оба бакета и сравнивает key + size и ETag (где с обеих сторон MD5), не опираясь ни на bulk.db, ни на журнал.
  • verifykeys (C2, C4): проверяет ключи, изменённые после сверки или переключения. Норма mismatched: 0.

Состояния ключа в key_state

Через эти состояния журнал и перенос делят ключи: кто первым создал строку, тот и владеет ключом.

synced и deleted не конечные: следующее намерение шлюза снова делает ключ dirty. Шлюз не смотрит на аренды и никого не ждёт. Ключ перенесён, когда synced_seq = change_seq и in_flight = 0.

Как процессы стыкуются

  • Ключ принадлежит тому, кто увидел его первым.Перенос копирует ключ, только если его нет в key_state. Всё, что хоть раз прошло через шлюз, переносит обработчик, а перенос пропускает (skipped_journal).
  • Шлюз никого не ждёт.Намерение пишется всегда, аренды обработчика и переноса на запись ELMA365 не влияют.
  • Изменённый во время копии ключ уходит обработчику.Перенос видит change_seq ≠ 0, ставит dirty, и обработчик перечитывает текущую версию из MinIO.
  • Копирование уступает журналу.Если обработчик отстаёт больше чем на JOURNAL_BACKLOG_MAX ключей, копирование встаёт на паузу (journal_lag). Листинг от журнала не зависит.
  • Инвентаризация начинается после включения шлюза.Листинг запускают после первой чистой проверки трассировкой (A6), не раньше часа после A4. Всё, что в окне переключения записано мимо шлюза, уже лежит в MinIO и попадёт в листинг.
  • Отдельного прохода по изменённым ключам нет.Всё, что менялось во время переноса, есть в журнале и закрывается обработчиком.
  • Без нового S3 работают только шлюз и листинг.Обработчик и копирование без DST_* не стартуют, а журнал копит грязные ключи до появления приёмника.

Процесс 1 · журнал
  • A1–A3: пользователь MinIO только на чтение, шлюз, nginx на служебном порту, замер задержки.
  • A4: nginx встаёт на :9000, MinIO уходит на 127.0.0.1, изменения идут через шлюз.

  • B1: DST_* в s3gw.env, включается s3gw-handler.

  • Дальше держит новое S3 актуальным до переключения ELMA365.
Процесс 2 · перенос
  • B2: согласовать SCHEDULE и порог деградации ELMA365.
  • B3: systemctl start s3gw-bulk, run сразу переходит к copy.
  • B4–B5: лимиты без перезапуска, export-errors, retry-errors.
  • B6: все диапазоны listed, нет pending, claimed, retry.

Процесс 1 · журнал

  • C2: read-only, очередь до нуля, verifykeys, шлюз и чтения на новое S3.
  • Журнал и обработчик работают обратно, новое S3 → MinIO.
  • C4 откат без потерь, C5 адрес minio2 переносится на новый сервер.
Процесс 2 · перенос

  • Задания в error и source_missing остаются в отчёте.
