# Маршрутизация S3 через nginx на minio2 (задача 07)

Задача: [`tasks/07-nginx-routing.md`](../tasks/07-nginx-routing.md). Конфиг: [`deploy/nginx/s3gw.conf`](../deploy/nginx/s3gw.conf).

Шлюз включается на самом `minio2`. Kubernetes, ingress и haproxy не меняются: haproxy по-прежнему шлёт всё на `10.10.0.12:9000`, только теперь этот адрес слушает nginx, а MinIO слушает `127.0.0.1:9000`.

```
ELMA365 ─► ingress-nginx ─► haproxy (k8s, без изменений) ─► 10.10.0.12:9000  nginx на minio2
                                                              │  GET/HEAD/OPTIONS s3elma365,
                                                              │  все запросы к другим бакетам ───► 127.0.0.1:9000 MinIO
                                                              └─ PUT/POST/DELETE s3elma365 ─► 127.0.0.1:9100 шлюз ─► MinIO
```

## Что меняется

| | Сейчас | С шлюзом |
|---|---|---|
| `10.10.0.12:9000` | MinIO | nginx |
| MinIO | `:9000` на всех адресах | `127.0.0.1:9000` |
| Чтения `s3elma365` | MinIO | nginx → MinIO |
| Изменения `s3elma365` | MinIO | nginx → шлюз → MinIO |
| Другие бакеты (`elma365-backups`, `-loki`, `-tempo`) | MinIO | nginx → MinIO, шлюз не участвует |
| Шлюз | — | `127.0.0.1:9100`, снаружи недоступен |
| После переключения на новое S3 (PIPELINE.md, C2) | — | чтения `s3elma365` тоже идут в шлюз, а он ходит в новое S3; другие бакеты по-прежнему прямо в MinIO |

- **Обход журнала исключён физически.** MinIO слушает только loopback, поэтому снаружи в него можно попасть только через nginx. Писать мимо шлюза могут только процессы на самом `minio2` (например, `mc` с алиасом на `127.0.0.1:9000`); на время миграции этого не делать.
- **Запасного пути мимо шлюза нет.** Если шлюз недоступен, запись в `s3elma365` получает `502`, а не уходит в MinIO без журнала (`proxy_next_upstream off`, один сервер в upstream).
- **Подписи не ломаются.** `Host` передаётся как пришёл (`$http_host`), путь и строка запроса тоже (`proxy_pass` без URI-части), заголовки с подчёркиванием не отбрасываются (`underscores_in_headers on`), длинные подписанные ссылки помещаются (`large_client_header_buffers 8 64k`).
- **Тела не буферизуются** ни в одну сторону (`proxy_request_buffering off`, `proxy_buffering off`); тайм-ауты 3600 с. Внешнее ограничение по-прежнему задаёт haproxy (60 с бездействия).
- **Лог только ошибок 5xx**: `/var/log/nginx/s3gw-5xx.log`. По нему видно `502` (шлюз лежит) и `503` (журнал недоступен).
- **Метка шлюза.** Шлюз добавляет к каждому пересланному запросу заголовок `X-S3gw-Request-Id` и пишет намерения под тем же id. По нему `s3gw.tracecheck` отличает изменения через шлюз от записей в обход. IP клиента для этого не годится: MinIO показывает в трассировке `X-Forwarded-For`, который ставит ingress, и он одинаков для обоих путей (проверено на стенде).

## Проверка

[`scripts/stand_pipeline.py`](../scripts/stand_pipeline.py) поднимает в Docker MinIO и `mc` тех же версий, что на `minio2` (`RELEASE.2025-09-07T16-13-09Z`, `RELEASE.2025-08-13T08-35-41Z`), и nginx 1.28 с этим конфигом. На этапе A [PIPELINE.md](../PIPELINE.md) он проверяет (дальше идут этапы B и C):

- политика RO из A1;
- трафик как от ELMA365 с `X-Forwarded-For`: спецсимволы в ключах, CopyObject, DeleteObjects на 400 ключей, multipart, подписанные PUT/GET;
- `mc admin trace --json --verbose` и `tracecheck`;
- `bulk list`;
- замер задержки;
- мгновенный откат.

Результат 2026-10-21 (тогда `scripts/stand_journal_only.py`): всё прошло, `tracecheck` нашёл ровно одну намеренную запись в обход и ни одного пропуска. 2026-10-22 стенды сведены в `stand_pipeline.py`: 68/68.

## Включение и откат

Пошагово: [PIPELINE.md](../PIPELINE.md), разделы A3–A4. Коротко:

1. Конфиг ставится сначала только со служебным портом `127.0.0.1:9080`, через него проверяется связка nginx → шлюз → MinIO.
2. Переключение (короткое окно, MinIO перезапускается): MinIO переводится на `--address 127.0.0.1:9000`, в конфиге включается `listen 10.10.0.12:9000`, затем `systemctl restart minio && systemctl reload nginx`.
3. **Мгновенный откат без перезапуска MinIO:** в `map` поменять `default s3gw_gateway` на `default s3gw_minio` и выполнить `nginx -s reload`. Запись идёт прямо в MinIO через nginx, журнал перестаёт пополняться.
4. **Полный возврат** (в окно): закомментировать `listen 10.10.0.12:9000`, вернуть прежний адрес MinIO, `systemctl reload nginx && systemctl restart minio`.

Пока новое S3 не стало основным, любой откат безопасен: MinIO остаётся источником правды. Изменения, прошедшие мимо журнала после отката, закрываются трассировкой с `--mark-dirty`, инвентаризацией заново (PIPELINE.md, A7) или сверкой (задача 10). После переключения на новое S3 мгновенный откат в `map` запрещён: откат только по PIPELINE.md, C4.

## Ограничения

- Адресация только path-style (`/s3elma365/<ключ>`), как у ELMA365 (`virtualHostedStyle: false`). Запрос в стиле virtual-host к `s3elma365` прошёл бы мимо шлюза; `tracecheck` покажет его как обход.
- Нужен достаточный `worker_connections` в `/etc/nginx/nginx.conf`: через nginx теперь идут все чтения, и каждое занимает два соединения. Значение по умолчанию в Debian/Ubuntu (768) мало; см. PIPELINE.md, A0.
- Старый конфиг прошлой миграции `/etc/nginx/conf.d/minio-migration.conf` (`:8083`) этим не затрагивается и в пути запросов не участвует.
