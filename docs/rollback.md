# Откат после переключения на новое S3

Задача: [`tasks/12-rollback-procedure.md`](../tasks/12-rollback-procedure.md).
Опирается на [`docs/gateway-design.md`](gateway-design.md).
Статус: черновик от 2026-10-21, переписан 2026-10-22 под работу только на `minio2`. Переключение и откат (PIPELINE.md, C2 и C4) прогоняются на стенде `scripts/stand_pipeline.py`.

## 1. Выбранный способ: тот же шлюз в обратную сторону

После переключения новое S3 становится основным, а старый MinIO — приёмником. Доступа к кластеру нет, поэтому haproxy не меняется: он по-прежнему шлёт весь трафик на `minio2:9000`, где его принимает nginx ([nginx-routing.md](nginx-routing.md), PIPELINE.md, A4). Шлюз, журнал и обработчик остаются те же, меняется только конфиг на `minio2`:

| | До переключения | После переключения |
|---|---|---|
| haproxy | всё на `minio2:9000` (nginx) | без изменений |
| nginx: изменения `s3elma365` | в шлюз | в шлюз |
| nginx: чтения `s3elma365` | прямо в MinIO | в шлюз |
| nginx: другие бакеты | прямо в MinIO | прямо в MinIO |
| шлюз отправляет запросы в (`GW_UPSTREAM`) | MinIO `127.0.0.1:9000` | новое S3 |
| обработчик читает из (`SRC_*`) | MinIO | новое S3 |
| обработчик пишет в (`DST_*`) | новое S3 | MinIO |
| журнал (`JOURNAL_DB`) | `journal.db` | новый файл `journal-reverse.db` |

Почему так:

- Код и испытания те же, что для прямого направления: нет отдельной утилиты, которую проверяли бы только на аварии.
- Не нужен листинг нового S3 и отбор по `LastModified`, как у запасного варианта ниже. Удаления тоже переносятся.
- MinIO на момент переключения уже содержит всё (по задаче 10 он совпадает с новым S3), поэтому массовый перенос в обратную сторону не нужен: переносятся только изменения после переключения.
- Переключение и откат делаются на `minio2` сменой конфига шлюза, его перезапуском и перезагрузкой nginx, без доступа к кластеру и без смены настроек ELMA365.

Запасной вариант на случай, если обратный шлюз не работает: скопировать в MinIO всё, что изменилось в новом S3 с момента переключения (`--newer-than` — время с `T_CUTOVER` с запасом, например `3d2h`):

```bash
mc mirror --overwrite --newer-than <время с T_CUTOVER> minio_new/s3elma365 minio_old/s3elma365
```

Он листит обе стороны (MinIO — по HDD, часы), не переносит удаления и опирается на `LastModified`, поэтому после него нужна сверка ключей (C1 в обратную сторону). Отбор по `--newer-than` и перезапись проверены на MinIO 2025-09-07 и `mc` 2025-08-13.

### Что нужно учесть при переключении (вход для задачи 11)

1. Запись на время окна останавливает сам шлюз: пока существует файл `GW_READONLY_FILE`, он отвечает `503` на изменения, а чтения пропускает.
2. Шлюз передаёт запросы ELMA365 без изменений (Host `elma.example.com`, path-style, регион `ru-central-1`), и подпись проверяет новое S3. Поэтому в новом S3 должны работать ключи доступа ELMA365. Проверка до окна: `scripts/check_new_s3_signature.py`.
3. Порт нового S3 открыт только для `minio2`, тогда изменения в обход шлюза невозможны. MinIO после переключения закрыт так же, как раньше (слушает только `127.0.0.1`, PIPELINE.md, A4), в `s3elma365` пишет только обратный обработчик.
4. Ключи доступа: шлюзу ничего не нужно (прозрачное проксирование), обработчику — чтение нового S3 и запись в MinIO.

## 2. Процедура отката

Команды: [PIPELINE.md](../PIPELINE.md), раздел C4. Кратко:

1. **Решение** (раздел 3). Объявить окно, предупредить пользователей.
2. **Остановить запись:** файл `GW_READONLY_FILE` на `minio2`. Чтения идут.
3. **Дождаться закрытия журнала:** нет незакрытых намерений, отставание обратного обработчика 0, каждый ключ в `error` разобран (перенесён или зафиксирован как допустимая потеря).
4. **Проверить** ключи, изменённые после переключения: `python -m s3gw.verifykeys --since <время переключения>` по `journal-reverse.db` сравнивает размер и ETag в обоих хранилищах. Это короткий список, не полный листинг.
5. **Вернуть шлюз на MinIO** (прямой конфиг со свежим журналом) и выключить обратный обработчик.
6. **Снять запрет записи и проверить ELMA365:** открыть старый файл, файл, созданный после переключения, создать новый, удалить тестовый.

Ожидаемая длительность шагов 2–6 — минуты плюс время дренажа очереди. Дренаж оценивается по метрике отставания обратного обработчика, которая видна всё время после переключения.

## 3. Критерии решения об откате

Откат рассматривается, если после переключения выполняется хотя бы одно:

- ELMA365 не может читать или писать файлы, и причина в новом S3, а не в сети или настройке, которую можно исправить за время, меньшее окна отката;
- обнаружена порча или потеря данных в новом S3;
- задержки операций с файлами выше согласованного порога дольше согласованного времени;
- отказ дисков или RAID нового сервера без возможности быстро восстановить избыточность.

Решение принимает владелец системы ELMA365 (кто именно — записать до переключения). Исполняет администратор по этой процедуре.

## 4. Срок поддержки отката

Откат поддерживается, пока работают обратный шлюз и обработчик и сохраняется старый MinIO. Рекомендуемый срок — не меньше двух недель после переключения (полный цикл рабочих процессов, включая месячные отчёты, если они есть). После окончания срока:

1. Обратная синхронизация останавливается.
2. Шлюз выводится из пути запросов: адрес `minio2` вручную переносится на новый физический сервер, на нём на время прокси на старый MinIO только для чтения объектов, которых нет в новом S3, с логом каждого такого обращения (PIPELINE.md, C5).
3. Старый MinIO работает ещё около месяца (прокси, старые бэкапы и логи других бакетов), в `s3elma365` в нём никто не пишет; затем выводится (задача 11).

После шага 1 откат возможен только через полную сверку и перенос в обратную сторону.

## 5. Базы данных ELMA365

Если базы ELMA365 переносятся вместе с файлами:

- Точка переключения файлов и баз одна: запись остановлена и для файлов, и для баз.
- При откате базы возвращаются на старый сервер вместе с изменениями после переключения (репликацией или переносом). Файлы, на которые они ссылаются, уже будут в MinIO: обратная синхронизация переносит все файлы, созданные после переключения.
- Если базы откатываются на снимок до переключения, файлы, созданные после, остаются в MinIO лишними. Их можно удалить по списку из `journal-reverse.db`, но только после подтверждения, что они не нужны.

## 6. Проверка на стенде (задача 06)

Шаги 1–4 проходит `scripts/stand_pipeline.py`; `kill -9` обработчика там проверяется в прямом направлении, во время обратного дренажа (шаг 5) — нет.

1. Стенд: MinIO, второе S3, шлюз, обработчик.
2. Прямое направление, перенос тестового набора, переключение по шагам из задачи 11.
3. Обратное направление: создать, перезаписать и удалить объекты через шлюз, включая multipart и `DeleteObjects`.
4. Откат по разделу 2. Проверить, что в MinIO все изменения после переключения, включая удаления.
5. Повторить с `kill -9` обработчика во время дренажа.

## Решения

- 2026-10-21. Основной способ отката — шлюз и обработчик в обратном направлении со своим журналом. Запасной — копия изменённого после переключения (`mc mirror --newer-than`, до 2026-10-22 — `migrator/copy_recent_dst_to_src.py`) со сверкой ключей.
- 2026-10-22. Доступа к кластеру не будет: переключение и откат делаются на `minio2` сменой `GW_UPSTREAM` и направления обработчика, запись на время окна останавливает шлюз (`GW_READONLY_FILE`).
- 2026-10-22. После срока отката адрес `minio2` переносится на новый сервер (делает владелец), там временный прокси на старый MinIO только для чтения недостающих объектов; haproxy не меняется. Другие бакеты не переносятся: новые бэкапы и логи пишутся в новое хранилище, старый MinIO живёт ещё около месяца.
